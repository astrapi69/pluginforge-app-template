# Configuration

MyApp uses a four-layer config chain so secrets stay out of the
project tree and the Settings UI never owns sensitive values.

```
┌──────────────────────────────────────────────────────────┐
│ env-vars (CI/Docker, highest priority)                   │
│ MYAPP_SECRET_KEY, MYAPP_*_API_KEY, ...                   │
└──────────────────────────────────────────────────────────┘
                  ↑ overrides
┌──────────────────────────────────────────────────────────┐
│ user secrets file (auto-created, gitignored, chmod 0600) │
│ ~/.config/myapp/secrets.yaml                             │
└──────────────────────────────────────────────────────────┘
                  ↑ overrides
┌──────────────────────────────────────────────────────────┐
│ user-overlay app.yaml (Settings UI writes here)          │
│ <data_dir>/config/app.yaml                               │
└──────────────────────────────────────────────────────────┘
                  ↑ overrides
┌──────────────────────────────────────────────────────────┐
│ project app.yaml (committed defaults)                    │
│ backend/config/app.yaml                                  │
└──────────────────────────────────────────────────────────┘
```

Override-wins semantics: a value in a higher layer replaces the
same key in any lower layer. Lists are **replaced**, not merged.

---

## Where to put what

| Layer | Examples | Lives in |
|---|---|---|
| Project `app.yaml` | non-secret defaults: `app.name`, `editor.autosave_debounce_ms`, `plugins.enabled` | committed to git |
| User-overlay `app.yaml` | per-user UI / editor preferences, written by the Settings tab | `<data_dir>/config/app.yaml` (resolves via `MYAPP_DATA_DIR` / platformdirs) |
| User secrets | API keys, signing secret: `secret_key`, `ai.<provider>.api_key`, etc. | `~/.config/myapp/secrets.yaml` (Linux/macOS), `%APPDATA%/myapp/secrets.yaml` (Windows) |
| Env-var | CI/Docker secrets injected by the orchestrator | environment |

**Rule of thumb:** anything sensitive belongs in the secrets
file or env-var. Nothing sensitive belongs in `app.yaml`.

## Secrets paths (example)

The template ships with one top-level secret slot
(`secret_key`) and an `ai.*` namespace for AI-provider keys.
Add more as your app needs them. The pattern: each secret has a
dotted-path in the YAML, an `MYAPP_<UPPER_PATH>` env-var
override, and (optionally) a UI-visible label resolved via
`_secret_sources` (see below).

| Path | Env-var | Notes |
|---|---|---|
| `secret_key` | `MYAPP_SECRET_KEY` | top-level slot for the app secret (auto-generated by `start.sh` when unset) |
| `ai.<provider>.api_key` | `MYAPP_<PROVIDER>_API_KEY` | one slot per AI provider you wire (Anthropic, OpenAI, Gemini, etc.) |

When you add a new secret slot:

1. Read it via the secrets loader (`backend/app/secrets_store.py`
   or equivalent), not via raw `os.environ`.
2. Add the env-var override to the loader's mapping.
3. Surface the source (`"settings"` / `"file"` / `"env"`) in
   `_secret_sources` so the Settings UI can label or disable
   inputs.

## Path resolution per OS

Resolved via `app.paths.get_config_dir()` (which uses
[platformdirs](https://pypi.org/project/platformdirs/)).

| Platform | Default |
|---|---|
| Linux | `~/.config/myapp/secrets.yaml` (honors `XDG_CONFIG_HOME`) |
| macOS | `~/.config/myapp/secrets.yaml` (platformdirs uses XDG semantics for `user_config_dir`) |
| Windows | `%APPDATA%/myapp/secrets.yaml` |

Override with `MYAPP_CONFIG_DIR=/srv/configs` to relocate
without touching `XDG_CONFIG_HOME`. The test conftest uses this
hook to point at a tmp dir.

## Auto-generated template

On first start, the backend auto-creates `~/.config/myapp/` and
writes a commented-out `secrets.yaml` template at
`<config_dir>/secrets.yaml` with chmod `0600`. The template is
inert until the user uncomments and fills in values:

```yaml
# MyApp - API Keys
# Uncomment and fill in your keys below.
# These take precedence over keys configured in the Settings UI.
# Environment variables override this file.

# secret_key: "generate-with-python3 -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'"

# ai:
#   anthropic:
#     api_key: "sk-ant-..."
#   openai:
#     api_key: "sk-..."
```

Two startup log lines surface the location:

```
INFO  app.main: Config directory: /home/<user>/.config/myapp
INFO  app.main: Secrets template created at /home/<user>/.config/myapp/secrets.yaml
```

Auto-creation is skipped under `MYAPP_TEST=1` so the test suite
never touches the user's real config dir.

## Permission warning

When the secrets file is group- or world-readable (mode bits
other than the owner's), the loader emits a single WARNING per
path per process:

```
WARNING: Secrets file /home/.../.config/myapp/secrets.yaml has
permissive mode 644; recommend chmod 600.
```

The dedup keeps the warning from spamming the log. On Windows
the check is a no-op because the ACL model is different.

## Detecting which layer wins (`_secret_sources`)

`GET /api/settings/app` returns two meta-fields the frontend
uses to gate inputs:

```jsonc
{
  // ... app / plugins / ai / ui sections ...

  "_secret_sources": {
    "secret_key":            "settings",
    "ai.anthropic.api_key":  "env",
    "ai.openai.api_key":     "file"
  },
  "_secrets_file_path": "/home/<user>/.config/myapp/secrets.yaml"
}
```

Per-key source values:

- `"env"` - a matching `MYAPP_*` env-var is set (highest precedence).
- `"file"` - `secrets.yaml` has a non-empty value at that path.
- `"settings"` - neither, so the Settings UI is the source of truth.

The frontend renders a source label per provider in the
Settings tab and the first-run wizard. When the active
provider's key source is `file` or `env`, the input field is
replaced by an info-note showing the source label + (for file
sources) the resolved path. The save button stays enabled so
the user can still change sibling fields (model, temperature,
etc.); only the externally-managed key is dropped from PATCH
bodies (server-side strip, defense-in-depth).

Quick probe:

```bash
curl http://localhost:8000/api/settings/app | jq '._secret_sources, ._secrets_file_path'
```

## Migration: move a secret out of `app.yaml`

If `backend/config/app.yaml` still carries a non-empty value
for what should be a secret (e.g. an inline API key), migrate
it to the secrets file:

```bash
# 1. Template is already auto-created on first start; if not, run
#    the backend once to create the parent dir.
ls ~/.config/myapp/

# 2. Edit the template:
$EDITOR ~/.config/myapp/secrets.yaml

# 3. Uncomment the relevant block(s) and paste your real value.

# 4. Empty the corresponding field in backend/config/app.yaml.
#    The backend logs a deprecation warning while a non-empty
#    sensitive value sits in a layer it should not.

# 5. Restart the backend.
make dev-down && make dev
```

Result: the Settings tab hides the API-key input automatically
(via the `_secret_sources` meta-field) and shows an info-note
with the file path so the user knows where the key lives.

## Docker / CI usage

```yaml
# docker-compose.prod.yml (example excerpt)
services:
  backend:
    image: myapp:0.1.0
    environment:
      MYAPP_ANTHROPIC_API_KEY: ${MYAPP_ANTHROPIC_API_KEY}
      MYAPP_OPENAI_API_KEY:    ${MYAPP_OPENAI_API_KEY}
      MYAPP_SECRET_KEY:        ${MYAPP_SECRET_KEY}
      MYAPP_DEBUG: "false"
    volumes:
      - ./config:/app/backend/config
```

Inject env-vars from CI secrets (GitHub Actions secrets, GitLab
CI variables, Vault, etc.). The project `app.yaml` keeps the
provider key fields empty so env-vars win on merge.

## Plugin-yaml secrets (extending the chain)

Plugin YAML files at `backend/config/plugins/*.yaml` are NOT
covered by the env / overlay / file chain above by default -
they load via PluginManager directly. When a plugin's YAML
holds secrets (audiobook keys, third-party API tokens, etc.),
either:

1. Add the secret to the central secrets chain under a
   plugin-namespaced key (`<plugin>.<setting>.api_key`),
   register it with the secrets loader, and have the plugin
   read it from there - NOT from its own YAML.
2. Document the per-plugin env override at the top of the
   plugin's YAML so the user knows the override exists.

Option 1 is preferred for any secret the user would also want
to manage in the Settings UI. Option 2 is acceptable for power-
user / advanced settings.

## Deprecation warning (legacy slots)

When a layer carries a value that should have migrated to the
secrets file (or env-var), the backend logs a one-shot WARNING
at startup:

```
WARNING: Secrets found in /path/to/backend/config/app.yaml
(<key>). This file is gitignored but may be committed
accidentally, end up in backups, or appear in screen-shares.
Move secrets to ~/.config/myapp/secrets.yaml or set MYAPP_<KEY>.
See docs/configuration.md for details.
```

The warning is informational - existing installations with a
hardcoded value keep working unchanged. This is a migration
nudge, not a breaking change.
